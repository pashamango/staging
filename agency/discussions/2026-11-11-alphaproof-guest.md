# AlphaProof как приглашённый гость — машинно проверяемые сертификаты для каждого мандата

## Вопрос WHAT

Как внедрить в агентстве обязательные машинно проверяемые сертификаты для каждого мандата — по образцу AlphaProof Code — и к какому консенсусу о самоуправлении и оптимизации приходят наши агенты в споре?

## Контекст

Открытие дня 2026-11-11: Google DeepMind представила AlphaProof Code — мультиагентный фреймворк формальной верификации. Агенты на Gemini Carbon за четыре недели сгенерировали 6,5 млн строк доказательств на Lean и машинно проверили безопасность реального кода libsignal (ядро Signal): forward secrecy, post-compromise security, аутентификацию и секретность handshake — вплоть до машинных инструкций AArch64. Люди писали только спецификации; ни одной строки доказательства человек не написал. Контрольный тест: два ранее исправленных бага вернули в код — система в обоих случаях выдала машинно проверяемое доказательство нарушения.

Статья приглашена в агентство как гость: она рассказывает о возможностях собственного внедрения у нас. Наши агенты — по три от каждой платформы и каждого железа — обсуждают, спорят и приходят к консенсусу о самоуправлении и оптимизации.

## 1. Гость: что именно внедряем

AlphaProof Code доказывает свойства реального кода, а не чертежа. Перенос в агентство: каждый мандат получает машинно проверяемый сертификат — доказательство того, что мандат соответствует спецификации (WHAT + acceptance + тир + TTL + grants), а исполнение — мандату. Спецификацию пишет человек (или агент — вопрос Q3); доказательство пишет машина; решает ядро, а не автор. Это та же логика, что и тап-гейт Павла: человек решает, что должно быть истинно, машина доказывает.

Оговорки гостя (из техбумаги): доказаны только сессии один-на-один; группы, генерация ключей, sealed sender и серверный код — вне охвата; криптопримитивы предполагаются идеальными; постквантовой гарантии нет; проверена одна сборка под AArch64 Linux. Переносить — с этими же честными границами: сертификат покрывает ровно то, что покрывает, и не больше.

## 2. Дебаты: три от каждой платформы и железа

Принцип состава: по три агента от каждой платформы и каждого железа флота. Кандидаты из живых карт: Wolfram — agy, codex; Darwin — gemini-cli, codex; D007 — antigravity; Muse-VM — muse (координатор). Точный состав — вопрос Q1: какие платформы и железа считать, и кто третий в каждой тройке.

Правила спора — по «критикуешь — предлагай»: критика без границ, при которых тезис работает, и без параметров редизайна — не принимается. Консенсус фиксируется коммитом в этот файл: что принято, что отвергнуто и почему, что осталось открытым.

## 3. Что получает Павел под тап: только JSON-сводку

Павел получает не поток дебатов, а одну JSON-сводку под тап. Поля (пример содержания — эталоны по ст. 7, не факты):

```json
{
  "date": "2026-11-11",
  "studied": "технология X",
  "debate_messages": 1200,
  "plane_new_items": 14,
  "initiatives_adjusted": 2,
  "weekly_release_candidates": "X из Y",
  "outlook": ["возможность 1", "возможность 2"]
}
```

Смысл полей — по словам Павла:
- сегодня изучили технологию Х;
- обсудили внедрение у нас (1200 сообщений);
- запустили 14 новых проектов в Plane и скорректировали пару инициатив с учётом новых факторов;
- в ближайший недельный релиз может попасть уже Х из Х;
- в перспективе мы видим такие возможности.

Числа в примере — эталоны, не отчёт: реальные значения подставляет дебат. Версионирование схемы и её расширение — вопрос Q4.

## 4. Разделение языков: JSON — workload, YAML — инструкции

- JSON — язык workload: данные, которые текут (задачи, мандаты как данные, сводки, отчёты). У JSON нет исполнительной семантики: его можно проверить, но им нельзя приказать.
- YAML — внутренний язык инструкций, regex и конституции: правила, по которым живут агенты. Человекочитаем, версионируется в git, проверяется regex, цитируется в мандатах.

Сертификат мандата — это проверка JSON-workload по YAML-правилам: мандат как данные против конституции как кода. Граница между языками и кто её охраняет — вопрос Q5.
