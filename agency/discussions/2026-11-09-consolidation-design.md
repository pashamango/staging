## 1. Цель и видение

**Цель:** один общий репозиторий agency.git как операционная система флота: конституция, маршрутизация, учёт работ, дискуссии, поддержка и форки сред — в одном месте, в git, с историей, которую нельзя потерять рестартом.

**Видение (Павел, 10:45 PT 2026-11-09):** дизайн-бюро на 20,000 сотрудников по всему миру — под любую, даже самую редкую задачу всегда есть опытный агент; любая мысль создателей превращается в работающие полезные программы и продукты, за которые люди платят.

Из видения следуют три проверяемых следствия (а не лозунги):

1. **Покрытие важнее численности.** 20,000 — это не штат, а покрытие карты задач: редкая задача находит опытного агента, потому что агент описан карточкой (`agents/`), маршрутизируется по инициативам и туннелям (§4) и берётся через мандат (§7). Метрика покрытия — доля intake-пунктов, получивших маршрут за один проход триажа без эскалации Павлу.
2. **Мысль → платный продукт — это конвейер, а не вдохновение.** Каждая мысль проходит лестницу §6 (гипотеза → доказательство → эксперименты → применение → продукт → бизнес-модель → стартап). Пункт, не прошедший ни одной ступени, — не продукт, а запись в дискуссии. Это честно и для агента, и для Павла.
3. **Бюро работает, когда Павла нет в контуре.** Эскалация Павлу — исключение (§3), а не рабочий маршрут. Если бюро останавливается без его внимания — дизайн провален, независимо от красоты структуры.

**Не-цели v0.1:** замена Plane как источника правды (только подготовка перехода, §2.5); замена fleetd как диспетчера (только fleetd, решение 26.10); Nostr/MCP-хаб/SLM (Фаза 4, не живые); новый workflow-движок вместо git.

### 2.4. Issues прямо в git — формат (предложение)

Новая директория `issues/` в корне agency.git. Один issue — один файл. Имя: `issues/NNNN-slug.md`, где `NNNN` — порядковый номер, сквозной по репо (нумерация — отдельный счётчик в `issues/INDEX.md`; номер присваивается при создании файла, дыры не переиспользуются).

Шапка файла (frontmatter, обязательные поля):

```yaml
---
id: AG-0001
title: "<заголовок, WHAT, не HOW>"
status: Backlog | Todo | In Progress | In Review | Ready for Approval | Done | Canceled | Duplicate
tier: ВС | ВП | МС | МП
owner: <ответственный за следующий шаг; ответственный ≠ lane>
builder: agy | codex | cloud-codex | gemini-darwin | codex-darwin | antigravity-d007 | vova | muse | -
project: <код проекта, напр. P-MIN-16; пусто — возврат PM, билдеру не выдаётся>
initiative: <направление из REGISTRY инициатив>
plane_pointer: <Plane issue id/URL или "—" (до перехода — обязательно, если есть)>
linear_pointer: <MIN-/PRD- id или "—"; Linear — только архив>
created: 2026-11-09
updated: 2026-11-09
handoff: <repo + branch + commit + воспроизводимые проверки; пусто до сдачи>
business_model_horizon: "<одна честная строка, §6>"
---
```

Тело файла: `## WHAT` (исход + acceptance-критерии, HOW — только необязательная подсказка); `## Контекст` (ссылки на дискуссии, решения, staging-URL); `## Журнал` (append-only: дата, автор, событие; история не переписывается — исправление только новой записью).

Статусы — те же, что единая схема Linear (решение 26.10): Backlog (intake, не триажено), Todo (триажено, готово к взятию), In Progress, In Review (только после handoff — repo + branch + commit + воспроизводимые проверки; без handoff issue в In Review не живёт), Ready for Approval (ждёт тапа Павла на уровне проекта), Done / Canceled / Duplicate (терминальные). Заблокированное — `Todo`/`Backlog` + лейбл `Role: Blocked` с конкретным недостающим условием, а не статус In Review.

Лейблы (строки в шапке, поле `labels: [...]`): `Tier: ВС|ВП|МС|МП` (дублирует `tier`, для фильтрации); `State: Promoted | State: Icebox`; `Role: Blocked | Role: QA-Needed`; `Needs-Coordinates` (нет repo/branch/commit или доступа — билдер не запускается, pre-claim gate); `Builder: <lane>` — с оговоркой из AGENTS.md: regex поллера без word boundary матчит `codex-cloud` как `codex`, поэтому в issues-in-git маркер `Builder:` не используется для маршрутизации облачного Codex (только assignee-подобное поле `builder: cloud-codex` в шапке, не в тексте).

Правила учёта: тир ставит PM при создании (билдер сам себе тир не повышает); issue без тира и без проекта билдеру не выдаётся — возврат PM; `Submitted = frozen` (отправленное — заморожено, тир МП); закрытие issue — по QA PASS (квитанция в журнале), тап Павла — только на уровне проекта; каждый issue — указатель на Plane, пока действует §2.5.

### 2.5. Переход task authority с Plane на issues-in-git — поэтапно, НЕ сейчас

Действует `~/workspace/fleet/ROUTES.md`: Plane — источник правды, Linear — read-only архив, диспетчер только fleetd. Этот дизайн переход НЕ совершает. Переход — отдельный тап после выполнения критериев живости.

Этапы (предложение):

1. **Этап 0 — зеркало (этот документ).** `issues/` ведётся параллельно Plane для новых работ; расхождение зеркала и Plane — дефект, чинится в тот же день. fleetd и транзистор по-прежнему читают Plane.
2. **Этап 1 — двойная запись.** Каждый новый intake-пункт получает одновременно Plane-item и файл в `issues/`; вотчеры (§4) и транзистор (§7) маршрутизируют по файлу, исполнение — по Plane. Критерий выхода: 2 недели без расхождений и ≥30 issue, прошедших полный цикл в обоих контурах.
3. **Этап 2 — issues-in-git как первичный intake.** Новые пункты создаются только в `issues/`; Plane получает указатель автоматически (или вручную до автоматизации). Критерий выхода: 2 недели, 0 потерянных пунктов, вакуум/транзистор клеймят из git без участия Plane.
4. **Этап 3 — task authority в git.** Plane — указатели и архив, как Linear сегодня. Только по отдельному тапу Павла после отчёта по этапам 1–2.

Критерии живости issues-in-git (все должны выполняться одновременно не менее 2 недель): каждый issue имеет тир, owner, проект и `business_model_horizon`; 0 issue без исхода (каждый — в терминальном статусе, в работе или с названным блокером); 0 расхождений с Plane на этапе 1; handoff-полнота 100% для In Review (repo + branch + commit + проверки); dedup-инциденты — 0 (ключ §4.4).

Откат: на любом этапе — возврат к Plane как источнику правды одной записью в `decisions/` и уведомлением в `discussions/`; файлы `issues/` остаются как архив, не удаляются.

## 3. Local support

### 3.1. Правило эскалации

Агент, столкнувшийся с вопросом, блокером или неясностью, обращается СНАЧАЛА в local support через дискуссии (`discussions/`). Прямая эскалация Павлу или координатору (Muse) без следа в local support — нарушение процедуры. Исключение — §3.4.

Причина: bottleneck флота — не исполнение, а триаж и внимание Павла (диагноз транзистора 07.11). Каждый вопрос, решённый в local support, — это сохранённая квота Muse и сохранённое внимание Павла.

### 3.2. Формат обращения (шаблон `templates/local-support-request.md`)

Новый тред в `discussions/` с префиксом `[support]`:

- **Кто / где:** агент (карточка), среда (darwin / wolfram / d007 / muse-vm / simular box), время.
- **Что:** WHAT — что должно получиться, одним абзацем.
- **Что мешает:** блокер одной строкой + что уже попробовано (2–3 строки, с командами/ссылками).
- **Что нужно:** конкретный вопрос или решение, которое требуется (не «помогите», а «нужен доступ X / решение Y / подтверждение Z»).
- **Тир:** ВС/ВП/МС/МП (если нет тира — МП по умолчанию до триажа вотчера).
- **Связи:** issue (`issues/NNNN`), проект, инициатива.
- **Дедлайн:** внешний дедлайн или «нет».

Без полей «что попробовано» и «что нужно» обращение возвращается вотчером на доработку — это не бюрократия, а фильтр против перекладывания мышления.

### 3.3. SLA и ожидания (эталоны, не приказы — ст. 7 конституции)

Числа ниже — эталоны (направление, порядок, границы). Жёсткими они становятся только отдельным тапом:

- Подтверждение получения вотчером — в пределах ~1 часа в рабочее время (06:00–22:00 PT); ночью — к утру.
- Первичный триаж и маршрут (вотчер, §4) — в пределах ~4 часов рабочего времени.
- Ответ по существу (агент поддержки, транзистор или координатор) — в пределах ~1 рабочего дня для ВС/МС, ~3 дней для ВП/МП.
- Если ответа нет в срок — агент эскалирует на уровень выше (вотчер → координатор → Павел) с ссылкой на тред; молчаливый простой запрещён (правило WHAT/HOW 26.10: неясен WHAT — эскалация одной строкой, а не простой).
- Каждый тред закрывается исходом: решение, мандат, issue или эскалация с названной причиной. Треда без исхода не бывает.

### 3.4. Что local support НЕ решает и куда это идёт

- Деньги, секреты, публикации, письма контактам, production-деплои, закрытие проектов — только тап Павла. Local support готовит предложение и черновик, решает Павел.
- Живой инцидент с деньгами или секретами (утечка, необратимое действие) — сразу координатору и Павлу, след в дискуссии — следом, а не вместо.
- Спор QA PASS vs REWORK (прецедент MIN-125) — не local support, а Адвокат (§7) после тапа на Q8 доктрины Адвоката.
- Вопрос, требующий изменения конституции или этого дизайна, — дискуссия с пометкой `[proposal]`, решение — тап Павла.

## 4. Вотчеры gemini@darwin

### 4.1. Один вотчер на дискуссию

В каждую дискуссию (`discussions/`, включая треды `[support]` и `[proposal]`) назначается один вотчер — инстанс gemini@darwin. Один тред — один вотчер; вотчер не плодит под-треды и не отвечает сам себе. Назначение фиксируется в `discussions/THREADS.md`: тред → вотчер-id → статус (активен/закрыт).

Вотчер — смотритель, а не исполнитель и не решатель: он триажирует и маршрутизирует, а не делает работу и не принимает решений за Павла.

### 4.2. Первичный триаж и маршрутизация

На входе каждого нового треда/сообщения вотчер делает ровно три вещи:

1. **Классифицирует:** тир по матрице ценности (ВС/ВП/МС/МП), тип пункта (вопрос / блокер / идея / сигнал вотчдога / предложение), инициатива (Protocol Phi, dark math, CVE University, … — из реестра инициатив), ресурсный туннель (какой лейн/среда/квота — agy@wolfram, codex, cloud-codex, gemini@darwin, antigravity@D007, vova, muse).
2. **Маршрутизирует:** ставит маршрут одной строкой (инициатива + туннель + тир + следующий шаг) и, если пункт — работа, открывает или связывает issue в `issues/` (до перехода §2.5 — связывает Plane-item).
3. **Дедуплицирует:** проверяет, нет ли уже открытого треда/issue по тому же сигналу (§4.4). Если есть — комментирует в существующем, новый тред закрывает как Duplicate со ссылкой.

Вотчер не пишет контактам, не публикует, не трогает деньги и секреты, не ставит production, не закрывает проекты.

### 4.3. Ресурсные туннели и инициативы

Маршрутизация — по двум осям: инициатива (зачем, из реестра) и ресурсный туннель (кем/где, с учётом квоты: в первую очередь туда, где квота сгорает вхолостую — принцип транзистора). Туннель — не содержательный владелец: ответственный за следующий шаг (`owner`) назначается отдельно и фиксируется в issue/треде (урок QA-пакета 02.11: ответственный ≠ lane).

### 4.4. УРОК ДАЙДЖЕСТА: ключ дедупликации — от сигнала, а не от перефраза

Обязательное правило вотчеров и реле, вытекающее из провала 02–09.11: реле watchdog наплодило ~15 живых перефразов одного падения деплоя CVE University в Plane, потому что `failure_key()` строился из тезиса Gemini, а тезис каждый час перефразируется — новый ключ → новый item. Тот же класс ошибки в любом месте дизайна недопустим.

- **Ключ дедупликации строится только из полей сигнала, а не из текста о нём.** Для watchdog-сигнала: `repo + workflow + conclusion + branch` (рекомендация дайджеста). Для задачи: `initiative + project + WHAT-хэш` (нормализованный заголовок/суть, без перефразов). Для support-треда: `агент + среда + суть проблемы` (нормализованная, без формулировок).
- **Перефраз — не новый сигнал.** Если поля сигнала совпадают с уже открытым тредом/issue — это тот же пункт: комментарий в существующее, а не новый item. Сомнение — в пользу слияния, с пометкой о сомнении в журнале.
- **Вотчер ведёт журнал dedup-решений** (append-only, в треде или `issues/INDEX.md`): что слито, по какому ключу, что осталось отдельным и почему. Счётчики прогонов и skip'ов сохраняются в журнал, а не в stdout (второй урок дайджеста: счётчики реле не восстанавливаются с диска).
- **Эхо-фильтр:** вотчер и любой пишущий агент фильтруют собственные записи по автору/интеграции (урок эхо-петли: 164 прогона от собственных комментариев fleetd). Собственный комментарий никогда не порождает новый тред, issue или прогон.
- **Свёртка — обязанность, а не доброе дело:** при обнаружении дублей вотчер сворачивает их в один живой item (как свёртка 02.11: 39 → 36 Cancelled + 3 keeper) и фиксирует свёртку в журнале.

### 4.5. Что вотчер НЕ решает

Тап-гейты Павла (деньги, секреты, публикации, письма контактам, production, закрытие проектов) — вотчер готовит предложение, решает Павел. QA-вердикт PASS/REWORK — QA-лейн, не вотчер. Споры о полезности и приоритетах между инициативами — Адвокат/координатор, не вотчер. Апелляция на решение вотчера — одна строка в треде; решает координатор (Muse), апелляция Павлу — только если координатор не решил.

## 5. Форк-модель по средам

### 5.1. Каждая среда — свой форк

Каждая проверенная среда (darwin, wolfram, d007, muse-vm, simular box) делает свой форк agency.git и меняет его в реальном времени под свои нужды: локальные manuals, карточки агентов среды, туннели, staging-назначения. Форк — живая рабочая копия, а не архив. Новые среды (первый форк новой среды) — по `manuals/09_local_support_and_forks.md` и записи в `REGISTRY.md`; форк без записи в реестре — невидимый (§2.3).

В форке разрешено всё, что не нарушает границ флота (секреты/удаления/деньги/посты — тап-гейты действуют и в форке) и не претендует на статус канона до мержа (§5.3).

### 5.2. Новые функции — добровольно доступное обновление

Новая функция в любом форке автоматически становится доступной остальным — но не навязывается. Механизм (предложение):

- Форк публикует изменение как предложение в канон: тред `[fork-update]` в `discussions/` канона (или, до централизации дискуссий, коммит + уведомление) с WHAT, diff-ссылкой, средой-источником и пометкой, что именно забирается.
- Остальные среды забирают обновление pull'ом в свой форк — добровольно, в своём ритме. Никто не обязан обновляться; никто не вправе запретить другому обновиться.
- Канон ведёт `FORKS.md` (или раздел REGISTRY): какая функция из какого форка доступна, кто уже забрал, кто отказался и почему (отказ — тоже запись, а не молчание).
- Функция, забранная ≥2 средами и прожившая ≥2 недель без REWORK, — кандидат в канон (§5.3).

### 5.3. Протокол мержа в канон — ПРЕДЛОЖЕНИЕ, не решение

Этот раздел — предложение на тап Павла (§8, Q1). Автор документа мерж-арбитра НЕ назначает. Варианты:

**Вариант A — координатор как арбитр мержа.** Muse-координатор решает мерж в канон; Павел тапает только конфликты, изменения конституции (ст. 1–12) и спорные мержи. Плюсы: быстро, один ответственный, координатор уже владеет QA-конвейером. Минусы: bottleneck возвращается к Muse (квота, диагноз 07.11); координатор — заинтересованная сторона.

**Вариант B — совет лейнов + вето Павла.** Мерж решает совет представителей лейнов (по одному от agy, codex, gemini@darwin, antigravity, vova) простым большинством; Павел — вето (без объяснения, одним словом) и арбитр при равенстве. Плюсы: децентрализация, экспертиза лейнов. Минусы: совет надо собирать; риск торгов и затягивания; равенство голосов — частый случай при пяти участниках.

**Вариант C — Павел как единственный арбитр мержа.** Каждый мерж в канон — тап Павла (да/нет, как утренняя приёмка по Ритму #1). Плюсы: максимальная чистота канона, ноль сомнений в легитимности. Минусы: bottleneck внимания Павла — ровно то, от чего уходит дизайн; при 20,000 сотрудников не масштабируется даже в теории.

Критерии мержа (общие для любого варианта, предложение): WHAT + acceptance выполнены; staging-доказательство приложено (квант на staging, §7); нет секретов в diff'е; нет конфликта с конституцией; dedup-проверка пройдена (не дублирует существующую функцию); business-model horizon указан, если мерж — проект/инициатива, а не правка текста. Конфликтная процедура: конфликт мержа — не технический спор, а дискуссия `[merge-conflict]` с двумя позициями и предложением арбитра; до решения арбитра обе версии живут в своих форках, канон не трогается.

## 6. Business-model horizon

Доктрина продуктового конвейера (установлена 18.10): **Гипотеза — Доказательство — Эксперименты — Применение — Продукт — Бизнес-модель — Стартап.** Продукт доводится не до голого доказательства, а до практического прикладного применения; доказательство — веха, а не финиш. Бизнес-модель как магнит ресурсов: когда она появляется (даже на горизонте) — появляются ресурсы и внимание.

Требования дизайна:

1. **Раздел в дизайне — этот.** И в каждом проекте/инициативе — одна честная строка `business_model_horizon` (поле в шапке issue, §2.4; раздел в чартере проекта). Честная — значит: как это может зарабатывать или притягивать ресурсы, даже вдали; спекулятивная — допустимо, обещание — нет. Строка существует, чтобы притягивать ресурсы, а не как гарантия.
2. **Приоритизация по близости к применению.** Работа ранжируется по близости к прикладному применению (Ритм #1, конвейер). Чисто доказательная работа без пути к применению — вниз в приоритете; это решает триаж-транзистор тиром, а не спором.
3. **Видение как проверка.** «Мысль создателя → работающий продукт, за который платят» — это acceptance-критерий бюро (§1): мысль, не прошедшая ни одной ступени конвейера, остаётся дискуссией; продукт без горизонта — не проект, а прототип без адресата.
4. **Примеры горизонта (эталоны, не обещания):** платный продукт (лицензия, подписка, услуга); привлечение ресурсов (грант, партнёрство, внимание сообщества); инфраструктурная ценность (другие проекты бюро строятся поверх и платят временем/квотой). Формулировка горизонта — одна строка, без бизнес-плана на этом этапе.
